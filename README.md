# UI Screens (`uis`)

**Design every screen of your app as plain HTML before you build it. The framework is shaped around AI coding agents.**

Building the screens first helps a lot. Every state, edge case and number gets decided while changes are cheap, and
the app build then has an exact target. UI Screens packages that workflow:

- **One HTML file per artboard.** No build step, no framework, no dependencies. Agents already write good HTML/CSS.
- **Shared tokens and components** (`kit/`). Every screen looks like the same product, and rebranding means editing one file.
- **A brief** (`BRIEF.md`). Canonical demo data and business rules, so screen 40 uses the same names, prices and dates as screen 1.
- **Interaction notes** in each screen (`<aside data-notes>`). These become the build spec.
- **Prototype links** (`data-goto="B4"`). The gallery shows the flow, links in and out, and lets you click through.
- **Feedback loops agents can use without eyes:** static lint plus an in-browser self-check (overflow, clipped text,
  missing icons, unknown classes, bad links, hard-coded colors), screenshots and flow contact sheets.
- **A hand-off.** `uis spec` writes a Markdown spec with a mermaid navigation graph for the agent that builds the app.
- **One-file sharing.** `uis export` writes the whole gallery as a single HTML file. Send it to anyone, and they open it with no install, no server and no folder.

![A flow contact sheet made by `uis sheet`](examples/plantpal/shots/_sheet-B.png)

It came out of a real project (88 screens across seller app, owner panel, admin and public site) where the screens
came first and made the app build dramatically smoother.

## Quick start

```bash
npm i -g ui-screens        # or: node /path/to/UI_Screens/bin/uis.js …
uis init ui --name "My App"
cd ui
uis new A1 "Welcome" --group-title "Onboarding"
uis new A2 "Sign in" --like A1
uis check                  # lint + render in headless Chrome
uis shot A1                # → shots/A1.png
uis sheet A                # → shots/_sheet-A.png (the whole flow)
uis serve                  # gallery at http://localhost:4400
uis spec                   # → SPEC.md for the build
uis export                 # → dist/my-app-screens.html, one file to share
```

Requires Node ≥ 18 and Chrome, Chromium, Edge or Brave for `check`, `shot` and `sheet` (set `CHROME_PATH` if it isn't found).

## Using it with an agent

`uis init` writes `AGENTS.md` into the project: the workflow and rules an agent should follow. Point your agent at it,
or install the Claude Code skill:

```bash
cp -r skills/ui-screens ~/.claude/skills/
```

Then ask: *"Design the onboarding and checkout flows for <app> in ui/. Include the error and empty states."*

The loop the agent runs:

```
plan manifest → uis new → fill from COMPONENTS.md + BRIEF.md → data-goto + notes
   → uis check (0 errors) → uis shot → look at the PNG → fix → uis sheet → next screen
```

## Project layout

```
ui/
  index.html          gallery: zoom, notes, hotspots, focus view (#B4), ←/→ to step through
  AGENTS.md           rules for agents
  BRIEF.md            canonical demo data + business rules
  COMPONENTS.md       copy-paste markup for every component
  SPEC.md             generated by `uis spec`
  kit/
    tokens.css        colors, spacing, radii, type (rebrand here)
    components.css    ~70 components: phone chrome, buttons, lists, forms, sheets, desktop shell, tables…
    uis.js            icon sprite (Lucide) + status bar + prototype links + self-check
    gallery.js        the gallery
  screens/
    manifest.js       window.UIS = { name, groups: [{ id, title, device, screens: [[code, title]…] }] }
    A1.html …
  styles/             optional per-group CSS
  shots/              PNGs
```

## Screen anatomy

```html
<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=402">
<title>B2 · Plant detail</title>
<link rel="stylesheet" href="../kit/components.css">
<script src="../kit/uis.js"></script>
</head>
<body>
<main class="artboard phone" data-code="B2" data-title="Plant detail">
  <div class="status-bar"></div>                       <!-- filled by uis.js -->
  <header class="top-bar">
    <button class="circle-btn" data-goto="B1"><svg class="i"><use href="#i-chevron-left"/></svg></button>
    <span class="title">Monty</span><span class="slot"></span>
  </header>
  <section class="content">…</section>
  <div class="bottom-bar"><div class="inner"><button class="btn accent block" data-goto="B3">Log watering</button></div><div class="home-indicator"></div></div>
</main>
<aside data-notes hidden>
  <p>1. Log watering → B3. Snooze moves the reminder 1 day.</p>
</aside>
</body>
</html>
```

Devices: `phone` 402×874, `tablet` 834×1194, `desktop` 1280×832. Add your own in the manifest with `devices: { watch: { w: 205, h: 251 } }`.

## Commands

| Command | What it does |
|---|---|
| `uis init [dir] --name X` | Scaffold a project (kit is vendored, so edit it freely) |
| `uis new CODE "Title" [--like CODE] [--tabs --web --sheet --scroll] [--group G --group-title T --device D]` | New screen + manifest entry |
| `uis list [--json]` | Screens, built status, outgoing links |
| `uis lint [CODE/GROUP…]` | Static: manifest ↔ files, artboard/code/title, unknown icons, unknown classes, bad `data-goto`, missing notes, inline SVG, remote images |
| `uis check [CODE/GROUP…]` | Lint plus a headless render: overflow past the artboard, text overflowing its box, missing sprite icons, broken images, hard-coded colors, content cut off at the bottom |
| `uis shot [CODE/GROUP…] [--scale 2]` | PNG per screen, auto-sized to the artboard |
| `uis sheet [GROUP…]` | One PNG of a whole flow with notes, so you can review consistency |
| `uis spec [--out file]` | Markdown hand-off: navigation graph, per-screen notes, links in and out |
| `uis export [GROUP…] [--out file]` | The whole gallery (or some flows) as one self-contained HTML file: screens, styles, images, notes and click-through all inlined |
| `uis icons` | Icon names in the sprite |
| `uis serve [--port]` | Static server for the gallery |

All checks print one issue per line (`CODE level type element — message`), support `--json`, and exit with code 1 on errors.

## Sharing screens

```bash
uis export                 # every flow → dist/<name>-screens.html
uis export B C             # only flows B and C
uis export --out review.html
```

The file is the full gallery: zoom, notes, hotspots, the focus view (`#B4` links work), and click-through between
screens. Everything is inlined (kit CSS and JS, group stylesheets, local images and fonts as data URIs), so it works
as an e-mail attachment, in Slack or Drive, or double-clicked from Downloads. It also works when uploaded to any static
host as-is. The kit is stored once, not once per screen, so even big projects stay small (the 7-screen example is about 120 KB).

Other options: `uis shot` and `uis sheet` give PNGs for quick pastes, `uis spec` gives the Markdown hand-off, and
the project folder itself can be deployed to any static host.

## Example

`examples/plantpal` is a small plant-care app with onboarding, a daily loop (including a sheet and an empty state) and a desktop admin page.

```bash
node bin/uis.js check --dir examples/plantpal
node bin/uis.js serve --dir examples/plantpal
```

## Design choices

- **Static HTML over a component framework.** Agents read and write it fluently, diffs stay legible, any browser
  renders it, and the output already is the CSS the real app can reuse.
- **System fonts and placeholder images (`.ph`)** keep renders deterministic and offline. Swap in web fonts in `tokens.css` if you want them.
- **The vendored kit is yours.** `uis init --force` refreshes it; your screens never depend on a package version.
- **Self-check runs in the page** (`kit/uis.js`) and writes its result to `<html data-uis-report>`. The CLI, the
  gallery and any other tool can read it.
